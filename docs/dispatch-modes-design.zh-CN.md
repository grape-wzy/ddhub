# ddhub 同步、异步分发与动态订阅设计

日期：2026-10-16。

状态：已按本轮确认的契约实现。接口与平台接入见 usage.zh-CN.md；验证项由双模式主机测试覆盖。

## 1. 执行模式与公共接口

通过用户配置头中的 `DDHUB_ASYNC_PROCESS_ENABLE` 在编译期选择模式。建议默认值为 `1`，保持现有发送入队的使用习惯。该配置必须在组件和所有调用方之间保持一致。

| 项目 | 同步模式：`0` | 异步模式：`1` |
|---|---|---|
| `ddhub_send()` | 直接分发目标 hub 的本条消息，完成后返回 | 将消息描述符入队，成功后调用全局通知 |
| 分发上下文 | send 调用者上下文 | process 调用者上下文 |
| `ddhub_process()` | 声明和实现均通过条件编译屏蔽 | 无参数，统一处理所有 hub |
| FIFO | 不承担同步分发职责 | 保留每个 hub 的静态 FIFO |
| 平台等待 | 由应用决定执行时机 | 由应用决定等待、唤醒与调用时机 |

异步模式的目标接口：

```c
typedef void (*ddhub_process_notify_t)(void);

ddhub_status_t ddhub_set_process_notify(ddhub_process_notify_t notify);
ddhub_status_t ddhub_process(void);
```

删除单 hub ID 的异步处理入口，将原有统一处理所有 hub 的能力收敛到 `ddhub_process(void)`，不再提供独立的 `ddhub_process_all()`。

组件继续使用现有平台 lock/unlock 注入方式。不增加 wait、ready、处理组或平台线程对象接口。

## 2. 同步发送

同步 send 取得目标 hub 的分发权后，在锁外执行订阅回调和消息完成回调，释放处理权后返回。成功意味着本条消息已经完成分发；不能用先入队再调用异步 process 的方式冒充同步完成。

- 同一 hub 已在分发时，再次向它发送返回 `DDHUB_BUSY`，包括回调重入和不同线程的竞争。
- 其他空闲 hub 可以同步分发；A → B → A 的递归在再次进入 A 时返回 `DDHUB_BUSY`。
- 失败不接收消息、不调用完成回调。
- 成功消息的完成回调执行一次，包括没有匹配订阅的消息。完成回调之后，组件不再访问该消息的 payload 或生产者上下文。
- 订阅回调和完成回调继承 send 的执行上下文。需要从 ISR 发送时，推荐开启异步模式，缩短中断内处理时间。

## 3. 异步统一处理与排空

全库只有一个异步消费执行者。它可以是线程、主循环或其他应用调度入口。并发或递归进入 process 返回 `DDHUB_BUSY`。

一次 process 按轮访问各 hub，每轮处理有限的当前消息批次，再复查全部队列；处理期间新入队的消息继续在本次调用中被消费，直到所有队列为空。持续发送可能使一次调用持续运行，不设固定消息数量或固定耗时上限。

最终空队列检查、释放本次处理权和清除全局 process 活动状态，必须在同一个平台临界区完成，并位于全部业务回调及完成回调返回之后。

- `DDHUB_OK` 表示该最终检查时刻所有 hub 的 `fifo.count` 都为零。
- 最终检查前已经入队的消息必须被本次排空循环再次看到。
- 最终检查后入队的消息属于后续工作，由新的发送通知安排处理。
- 不保证函数实际返回到调用者时队列仍为空，因为生产者可以在最终临界区结束后立即发送。
- 排空以消息队列状态为依据，不以通知次数为依据。`fifo.pending` 可作为本轮配额；是否仍有消息以 `fifo.count` 为准。

链表写者互斥与 FIFO、process 准入解耦。注册或注销的长扫描不再单独阻挡消息出队，也不再成为 process 因元数据繁忙而留下消息的原因。

## 4. 全局通知与平台接入

所有成功的异步 send 调用同一个 `process_notify(void)`，不传递 hub ID。通知在发送者上下文执行，包含 ISR 发送场景；绑定函数必须支持实际使用的上下文。

- 通知钩子在串行启动阶段配置，支持未绑定钩子的轮询使用方式。
- 实际通知调用必须在释放平台锁和内部锁之后进行。
- 失败的 send 不发布成功入队通知。
- 解除阻挡后若有需要继续处理的消息，可以补发同一个全局通知。
- 通知用于安排后续 process；异步适配器应避免依赖通知回调内递归调用 process 来完成排空。

裸机可以在主循环直接调用 process，不绑定通知。RTOS 可以用全局通知释放一个能保留唤醒的信号量，消费线程等待后调用 process。只有一个消费者，因此不要求多等待者广播。

处理期间产生的二值信号量通知可以在消息排空后仍有效，使下一次等待立即返回并触发一次空处理。这种冗余处理允许存在；应用不能在 process 结束后无条件清除可能包含新发送的通知。

## 5. 处理中注册与生效边界

允许目标 hub 正在分发时注册新订阅，不因 hub 的 processing 状态单独返回 `DDHUB_BUSY`。

新订阅成功注册后立即进入正常订阅链表，保持原有排序：priority 数值较小的先执行，同优先级按注册顺序执行。

**新订阅不参与已经开始分发的当前消息，从下一条消息开始参与。** 下一条消息可以仍由同一次 process 调用消费；同步模式下则是下一条成功同步发送的消息。注册本身不触发回调，不重放当前消息。

例如 A、C 的优先级分别为 10、30。A 回调中注册优先级为 20 的 B：

```text
当前消息：A → C
下一条消息：A → B → C
```

可使用注册序号实现该边界：每次成功发布注册记录新的序号，每条消息开始分发时捕获上限，只调用属于该上限范围的订阅。注销后同地址重新注册也视为新订阅。序号表示及回绕处理不得改变这一契约。

该边界使用数值状态，不依赖一个允许被注销、释放的旧尾节点地址。寻找下一条符合边界的订阅时，在平台保护内跳过本条消息开始后注册的节点，再标记选中的节点，避免锁外持续追逐新追加节点。

## 6. 注销、遍历与节点生命周期

process 不冻结整个 hub 的注销。当前仍被调度器使用、后续还可能读取的节点受保护，注销它返回 `DDHUB_BUSY`；其他节点允许摘除。

注销在 process 到达该节点前提交成功，则当前消息也跳过该订阅。注销成功后，调度器不再访问该节点。节点与业务对象的其他并发操作仍由调用方协调生命周期。

实现必须满足：

1. 节点选择、活动节点标记、所需字段读取和遍历推进使用同一个平台保护；业务回调在锁外执行。
2. 不跨回调保存未受保护的后继节点指针。
3. 当前节点的保护覆盖回调结束后的最后一次结构访问；完成后继选择和活动节点切换之后，才解除旧节点保护。
4. 最终入链和摘链指针更新在平台保护内进行。
5. 注销若在锁外完成长扫描，提交摘链前必须在平台保护内重新检查目标是否已成为活动节点。

例如 A 回调执行时注销 B，将 A.next 从 B 改为 C；A 回调返回后，process 在平台保护内读取更新后的 next，自然跳过 B。

注册、注销的长扫描可以继续通过链表写者标志串行化。两个链表写者竞争时仍可能返回 `DDHUB_BUSY`；这与 process 冻结整个 hub 是不同的规则。process 自身不等待该写者标志。

## 7. 验证范围与结果

- 分别构建同步、异步模式；验证同步构建没有 process 声明和链接符号。
- 同步 send 的直接完成、同 hub 重入拒绝、跨 hub 分发及完成回调生命周期。
- 多生产者与唯一异步消费者，处理期间自发送或跨 hub 发送，以及按轮排空。
- 最终空检查与退出之间的发送交接，确认新的发送能安排后续处理。
- 处理中注册从下一条消息生效，覆盖不同优先级、同优先级和同地址重新注册。
- 当前节点注销返回 BUSY；其他节点安全摘除，覆盖注销后继、尾节点以及回调内注销。
- 注册、注销与游标推进的受控并发交错，确认没有遗漏链表更新或访问已释放节点。
- 轮询和二值信号量两种接入方式，覆盖处理期间通知及排空后的冗余唤醒。
